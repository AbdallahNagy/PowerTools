# How XrmToolBox and Power Platform ToolBox package, distribute, version and host tools

Research ticket: AbdallahNagy/PowerTools#96, part of the "Community tools v1" map (#95).

**Question.** How do XrmToolBox (XTB) and Power Platform ToolBox (PPTB) package, distribute, version and host third-party tools? The questions are: what the manifest contains, how the catalog is built and reviewed, how updates and host-version compatibility work, what the host APIs offer (connections, multiple connections, settings, files, notifications), and what pain points authors and users report. The goal is lessons for our own format, not compatibility with theirs.

**Date and scope.** Researched 2026-11-03. Everything here comes from public sources: the documentation sites, the source repositories, the NuGet and npm registry APIs, and public GitHub issues. I did not install or run either app. Source versions read:

| Source | Version or commit read |
|---|---|
| XrmToolBox app | Latest release `v1.2026.9.78` (2026-09-30), `master` at `7bb5743e` |
| `XrmToolBoxPackage` (author SDK on NuGet) | Latest `1.2025.10.74` (2025-10-31) |
| PPTB desktop app | Latest stable `v1.2.7` (2026-10-12), `dev` at `152f482d` (2026-10-30) |
| `@pptb/types` (author SDK on npm) | `latest` = `1.2.7`, `beta` = `1.2.8-beta.1` |
| PPTB docs / intake pipeline / website | `pptb-docs-web@22cce93c`, `tool-management@9e20244f`, `pptb-web@addbcac0` |

**Labels.** **Observed** means read directly in a cited source. **Inference** means my reading of what the observations imply. **Recommendation** means a proposal for Power Tools. Both projects call their extensions "plugins" or "tools" in places. This report says "tool" for theirs and "community tool" for ours, and keeps literal identifiers (for example the XTB `Plugins` folder) as they are spelled.

## Short answer

- **XrmToolBox** tools are .NET Framework WinForms assemblies, discovered through MEF. They are packaged as **NuGet packages on nuget.org** with a `Plugins/` folder. The catalog ("Tool Library") is a **Dataverse-backed Power Pages portal** that lists only tools an administrator has validated. The client installs a tool by downloading the `.nupkg` and copying its `Plugins/` parts into one shared folder. Host compatibility is a **marker NuGet dependency** on an id `XrmToolBox` that does not exist on nuget.org, checked against a host-side floor. Tools run **in the host process with full trust**, receive a live `IOrganizationService`, and use .NET directly for files and settings. The main reported pain is **DLL conflicts** between tools that share one folder and one AppDomain.
- **Power Platform ToolBox** tools are web apps, published by the author to **npm** with PPTB fields in `package.json`. The author submits the npm name on the website. Automated validation and a one-time human intake review follow. A CI pipeline then **re-packs the npm package into a `.tar.gz` of `package.json` + `dist/`**, uploads it to Azure Blob, and records a SHA-256 in the registry. A **daily job pulls new npm versions** and republishes them after automated validation only. Compatibility uses `features.minAPI` against a host floor `MIN_SUPPORTED_API_VERSION`, the same two-number model as XTB. Tools run in a per-tool Electron `BrowserView` on a custom protocol, with an injected CSP and a typed `toolboxAPI` / `dataverseAPI` bridge. Tools never see tokens. Network access beyond Dataverse goes through **consented CSP exceptions**, and file access goes through **user-picked paths**. Optional native **.NET workers** run as unsandboxed child processes after a separate consent.

## Side-by-side

| Aspect | XrmToolBox | Power Platform ToolBox |
|---|---|---|
| Tool runtime | .NET Framework 4.8 WinForms `UserControl` in the host process (MEF export) | HTML/JS in an Electron `BrowserView` on `pptb-webview://`; optional .NET console "workers" over stdio JSON-RPC |
| Package format | NuGet `.nupkg`; tool DLLs under `lib/<tfm>/Plugins/` | npm package (`package.json` + `dist/`); the registry stores a re-packed `.tar.gz` |
| Manifest | nuspec fields + MEF `ExportMetadata` attributes in code | `package.json` (with PPTB fields `displayName`, `icon`, `contributors`, `configurations`, `features`, `cspExceptions`) + optional `pptb.config.json` |
| Where authors publish | nuget.org | npmjs.com |
| Catalog backend | Power Pages Web API `https://www.xrmtoolbox.com/_api/mctools_plugins` (Dataverse `mctools_*` tables) | Supabase DB + `registry.json` fallback on Azure Blob, built by GitHub Actions |
| First listing | Register the NuGet id on the portal; an admin validates (docs: "a few days") | Submit the npm name; automated checks + manual review (docs: "48-72 hours") |
| Later versions | Read from NuGet; whether the portal re-reviews them is not documented | Daily cron detects the new npm version; automated validation only, then republished |
| Trust tiers | Validated or not listed; MVP flag and ratings shown | Unverified (listed) vs **Verified** (separate human review, 1-2 week SLA, nightly governance can revoke it) |
| Host compatibility | `xtbDependencyVersion` must be ≥ host floor `MinCompatibleVersion` and ≤ host version | `minAPI` must be ≥ `MIN_SUPPORTED_API_VERSION` and ≤ host version; no `minAPI` means compatible |
| Integrity on install | No hash or signature check seen in `DownloadPackage` | Registry carries a SHA-256, but no verification seen in `downloadTool`/`extractTool` (tool UI); .NET worker packages do get a SHA-512 check |
| Update apply | Files are locked, so the update is staged in `Update.xml` and applied on restart | Staged extract, then swap; the docs say updates are atomic |
| Connections | `Service` (IOrganizationService) + `ConnectionDetail`; `MultipleConnectionsPluginControlBase` for more | `connections` count/range (0-10) in the manifest; `connectionTarget` slot on each Dataverse call; no tokens exposed |
| Settings | `SettingsManager` XML per assembly in `%AppData%\MscrmTools\XrmToolBox\Settings` | `toolboxAPI.settings` key/value per tool; removed on uninstall |
| Files | Unrestricted (.NET) | Only paths the user picked through `selectPath`/`saveFile`, per tool instance |
| Notifications | In-tool notification bar, status bar, Windows toasts | `utils.showNotification`, event bus |
| Network | Unrestricted | CSP `connect-src 'self'` + consented `cspExceptions`; `webSecurity: false` (CORS off) |
| Enterprise control | Registry keys: allow-list of tools, extra catalogs, disable updates and telemetry | Private marketplace sources (registry JSON over HTTPS/SAS); built-in source can be turned off |

## XrmToolBox

### Packaging and manifest

- **Observed.** A tool is a .NET assembly. The host discovers it with MEF: `PluginManagerExtended` builds a `DirectoryCatalog` over the Plugins folder and imports `IXrmToolBoxPlugin` exports with `IPluginMetadata` ([PluginManagerExtended.cs L95](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox/PluginManagerExtended.cs#L95)).
- **Observed.** The in-code manifest is just `Name`, `Description`, `SmallImageBase64`, `BigImageBase64`, `BackgroundColor`, `PrimaryFontColor`, `SecondaryFontColor` ([IPluginMetadata.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.Extensibility/Interfaces/IPluginMetadata.cs)). The host caches a richer scanned manifest locally: id, assembly file, interfaces, categories, version, usage count, rating ([Manifest/PluginMetadata.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.Extensibility/Manifest/PluginMetadata.cs)).
- **Observed.** Required nuspec fields: `id`, `version` (must equal the assembly version, or the Tool Library keeps showing an update), `title`, `authors`, `iconUrl` (your own icon; tools without one are refused), `projectUrl`, `description`/`summary`, `releaseNotes`, and a `tags` list that includes `XrmToolBox`. The package must declare a dependency with id `XrmToolBox` at the minimum host version, and the tool DLL must sit in a `Plugins` subfolder ([Deploy your tool in Tool Library](https://www.xrmtoolbox.com/documentation/for-developers/deploy-your-plugin-in-plugins-store/)).
- **Observed.** That `XrmToolBox` dependency is a **marker**. `https://api.nuget.org/v3-flatcontainer/xrmtoolbox/index.json` returns 404, so no such package exists. The SDK authors compile against is a different package, `XrmToolBoxPackage` (latest 1.2025.10.74) ([nuget.org/packages/XrmToolBoxPackage](https://www.nuget.org/packages/XrmToolBoxPackage)). As one example, FetchXML Builder 1.2026.9.2 declares `XrmToolBox [1.2025.10.74, )` and tags `XrmToolBox,Plugins,FetchXML,Builder` (NuGet registration API, `cinteros.xrm.fetchxmlbuilder`).
- **Observed.** The validation checklist also covers behaviour: large and small images, a layout that resizes, a tool that opens with no connection and asks for one when needed, and long operations kept off the UI thread ([Tool validation check list](https://www.xrmtoolbox.com/documentation/for-developers/deploy-your-plugin-in-plugins-store/plugin-validation-check-list/)).
- **Observed.** About 609 nuget.org packages carry the `XrmToolBox` tag (NuGet search `tags:XrmToolBox`, 2026-11-03).

### Catalog: how it is built and reviewed

- **Observed.** An author registers the NuGet package id on the portal, and the portal reads the package metadata. "An administrator must review and validate" the tool, which can take a few days. Since 2018-03-27 the Tool Library shows only validated tools ([Deploy page](https://www.xrmtoolbox.com/documentation/for-developers/deploy-your-plugin-in-plugins-store/)).
- **Observed.** The client reads `https://www.xrmtoolbox.com/_api/mctools_plugins?$expand=mctools_ContactId($select=mctools_ismvp)` and appends `$filter=statuscode eq 180000000`, a custom "validated" status reason ([ToolLibrary.cs L449-L519](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/ToolLibrary.cs#L449-L519)). Catalog rows use `mctools_*` columns: name, authors, description, categories, download URL, file list, open-source flag, license URL, `requirelicenseacceptance`, logo URL, `xrmtoolboxversiondependency`, NuGet id, version, latest release note, download counts, ratings, MVP flag ([XtbPlugin.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/AppCode/XtbPlugin.cs)).
- **Inference.** The `_api` path, the `mctools_` prefix, the status-reason filter and the `xrmtoolboxdev.microsoftcrmportals.com` host in the same file all point to the catalog being a Power Pages site over Dataverse. The catalog therefore keeps its own copy of the metadata, separate from NuGet.
- **Observed.** The catalog keeps a per-tool **file list** (`mctools_files`). The client uses it to decide whether a tool is installed and which files to delete, and it refuses to delete a file that another installed tool also lists ([ToolLibrary.cs L652-L688](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/ToolLibrary.cs#L652-L688)).
- **Observed.** Users and administrators can add extra catalogs: the `AdditionalRepositories` setting, or the registry keys `HKCU|HKLM\SOFTWARE\MscrmTools\XrmToolBox\Repositories`. These may be `http(s)` or `file` URLs ([ToolLibrary.cs L53-L76](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/ToolLibrary.cs#L53-L76), [ITSecurityChecker.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.Extensibility/ITSecurityChecker.cs)).

### Install, update and uninstall

- **Observed.** On install, the client downloads the `.nupkg` (http, https or file) into `NugetPlugins/<id>.<version>` and copies every part whose path contains `/plugins/` into the shared Plugins folder ([ToolLibrary.cs L225-L321](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/ToolLibrary.cs#L225-L321)). I found no hash, signature or package-source check in that path. A search of the file for `Hash`, `Signature` and `sign` found nothing.
- **Observed.** Assemblies already loaded are locked. Updates are therefore written to `Update.xml` (and deletions to `Deletion.xml`) and applied after `Application.Restart()` ([ToolLibrary.cs L555-L623](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/ToolLibrary.cs#L555-L623)).
- **Observed.** The installed version is the assembly version from the local manifest. An update is offered when that version is lower than the catalog `mctools_version` ([ToolLibrary.cs L119-L222](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/ToolLibrary.cs#L119-L222)). This explains the docs rule that the package version must equal the assembly version.
- **Observed.** The Tool Library can list older NuGet versions and marks each one `(incompatible)` when its minimum host version is above the running host, or below a breaking-change floor ([XtbPluginVersion.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/AppCode/XtbPluginVersion.cs)). Release notes come live from the NuGet registration `catalogEntry`.
- **Observed.** If a tool requires license acceptance, a dialog must be accepted before install ([ToolLibraryForm.Processing.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/Forms/ToolLibraryForm.Processing.cs)).

### Compatibility with host versions

- **Observed.** A tool is `Compatible` when its declared host dependency is ≥ `MinCompatibleVersion` (hard-coded `1.2015.12.20`) and ≤ the running host version. Otherwise it is `DoesntFitMinimumVersion` or `RequireNewVersionOfXtb`, and the install action becomes `Unavailable` ([ToolLibrary.cs L39, L835-L853](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.ToolLibrary/ToolLibrary.cs#L835-L853)). A missing or unparsable dependency gives `Other`, which is also not installable.
- **Inference.** One number does two jobs here: "the lowest host I need" and "the API generation I was built against". The only way to retire old API is to raise the global floor, which drops every older tool at once.

### Host API (what a tool can use)

- **Connections. Observed.** `PluginControlBase` gives the tool `Service` (a live `IOrganizationService`) and `ConnectionDetail`. It raises `ConnectionUpdated`, and the host calls `UpdateConnection(...)` to swap the connection. That call can re-invoke a tool method by name through reflection ([PluginControlBase.cs L54-L172](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.Extensibility/PluginControlBase.cs#L54-L172)). `ExecuteMethod` asks for a connection when none exists.
- **Multiple connections. Observed.** `MultipleConnectionsPluginControlBase` adds `AdditionalConnectionDetails` (an `ObservableCollection<ConnectionDetail>`), `AddAdditionalOrganization()`, `RemoveAdditionalOrganization()`, and an abstract `ConnectionDetailsUpdated` ([MultipleConnectionsPluginControlBase.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.Extensibility/MultipleConnectionsPluginControlBase.cs)). The count is open-ended and not declared in the manifest.
- **Settings. Observed.** `SettingsManager.Instance.Save(Type, object, name)` / `TryLoad<T>` serialize XML to `Settings\{AssemblyName}{_name}.xml` under `%AppData%\MscrmTools\XrmToolBox` ([SettingsManager.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.Extensibility/SettingsManager.cs), [Paths.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.Extensibility/Paths.cs)). Nothing enforces the per-tool naming. Any tool can read any file.
- **Files, network, processes. Inference.** The host offers no API and no restriction for these. Tools are ordinary .NET code in the host process.
- **Work and notifications. Observed.** `WorkAsync(...)` (a BackgroundWorker with a progress/cancel overlay), `ShowInfo/Warning/ErrorNotification` (an in-tool bar), `LogInfo/Warning/Error` with `OpenLogFile`, `ShowErrorDialog`, and `HandleToastActivation` for Windows toasts ([PluginControlBase.cs L185-L559](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.Extensibility/PluginControlBase.cs#L185-L559); [Use Notifications](https://www.xrmtoolbox.com/documentation/for-developers/Use-Notifications/)).
- **Opt-in interfaces. Observed.** Tools add host features by implementing interfaces: `IGitHubPlugin`, `IPayPalPlugin`, `IHelpPlugin`, `IStatusBarMessenger`, `IDuplicatableTool` (pass state to a cloned tab), `IShortcutReceiver`, `IMessageBusHost` (tool-to-tool messages), `IAboutPlugin`, `ISettingsPlugin`, `IPrivatePlugin` (no usage telemetry), `INoConnectionRequired`, `ICompanion` (docked side panel) ([Interfaces](https://www.xrmtoolbox.com/documentation/for-developers/interfaces/)).
- **Enterprise controls. Observed.** Registry values under `SOFTWARE\MscrmTools\XrmToolBox`: `AllowedPlugins` (substring allow-list), `IsCheckForUpdateDisabled`, `IsStatisticsCollectDisabled`, `IsDisabled`, and `Repositories` ([ITSecurityChecker.cs](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox.Extensibility/ITSecurityChecker.cs)).

### Reported pain points

- **Shared-folder DLL conflicts. Observed.** All tools share one Plugins folder and one AppDomain. A missing dependency is resolved by scanning **every** tool's subfolder ([PluginManagerExtended.cs L30, L246-L275](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox/PluginManagerExtended.cs#L246-L275)). This has caused real breakage:
  - Plugin Registration 3.2023.12.3 failed with `ReflectionTypeLoadException` because `Microsoft.Bcl.AsyncInterfaces` 6 was missing. Installing an unrelated tool that shipped that DLL made it work, and the maintainer had to rebundle dependencies ([PluginRegistration#132](https://github.com/Innofactor/PluginRegistration/issues/132), Dec 2023).
  - FetchXML Builder's release notes warn that it shares the DockPanel library with Plugin Trace Viewer, and that an outdated Plugin Trace Viewer causes a `FileNotFoundException` until its DLL is deleted by hand ([FetchXMLBuilder 1.2018.0.1005](https://github.com/rappen/FetchXMLBuilder/releases/tag/1.2018.0.1005)).
- **One bad assembly blocks loading. Observed.** A `ReflectionTypeLoadException` during composition shows an "invalid plugins" dialog and rethrows ([PluginManagerExtended.cs L104-L133](https://github.com/MscrmTools/XrmToolBox/blob/7bb5743e0bf0570a55ec6c0afe15be6c5f18d468/XrmToolBox/PluginManagerExtended.cs#L104-L133)).
- **Host and shared-library updates break connections. Observed.** After a connection-control update, online connections failed with `Method not found: ...OrganizationDetail.set_SchemaType`. The users' fix was a full uninstall, wiping the Roaming folder, and reinstalling ([XrmToolBox#1320](https://github.com/MscrmTools/XrmToolBox/issues/1320), Feb-Mar 2024, still open).
- **Restart to update. Observed** in code (above). Every update to a loaded tool needs an app restart.
- **Version discipline. Observed.** A mismatch between the package and assembly versions causes a permanent "update available" ([Deploy page](https://www.xrmtoolbox.com/documentation/for-developers/deploy-your-plugin-in-plugins-store/)).
- **Inference.** The registry `AllowedPlugins` policy exists because enterprises need to restrict full-trust tools. XTB has no per-tool permission model to offer them instead.

## Power Platform ToolBox

### Packaging and manifest

- **Observed.** The manifest is `package.json` at the root of the distribution ([Package Manifest](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/manifest/page.mdx)):
  - **Required:** `name` (scoped npm name), `version` (SemVer), `displayName`, `description`, `main` (entry HTML relative to `dist`), `icon` (an SVG path inside `dist`, `fill="currentColor"` for theming; URL icons are no longer supported), `license` (one of MIT, Apache-2.0, BSD-2/3-Clause, GPL-2.0, GPL-3.0, LGPL-3.0, ISC, AGPL-3.0-only), `contributors` (each with a `name`), and `configurations.repository`.
  - **Optional:** `configurations.website` and `readmeUrl` (raw.githubusercontent.com only).
  - **`features`:** `connections` (an integer 0-10, or `{min,max}`; added in 1.2.7, replacing the deprecated `multiConnection`/`connectionRequirement`), `minAPI` (SemVer), and `enabledForPowerPlatformAPI`.
  - **`cspExceptions`:** per directive (`connect-src`, `script-src`, `style-src`, `img-src`, `font-src`, `frame-src`, `media-src`), each entry with `domain`, plus optional Markdown `exceptionReason` and `optional`.
- **Observed.** A second, optional file, `pptb.config.json`, holds contracts that are versioned separately from the package. `invocation` (version, capability tags, prefill and return schemas) covers tool-to-tool calls. `agents` (version, `headless`, `invokable`, modes, `headlessEntry`) covers MCP agents. `workers` declares .NET workers and requires `features.minAPI` ([Tool Configuration](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/pptb-config/page.mdx)).
- **Observed.** The author SDK is `@pptb/types`. It ships the `.d.ts` files plus a `pptb-validate` CLI that is "a standalone copy of the review rules", with `--json` and `--skip-url-checks` for CI ([Local Tool Validation](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/validation/page.mdx); [packages/types/package.json](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/packages/types/package.json)). The types package version is kept equal to the app version ([TOOL_VERSION_COMPATIBILITY.md](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/docs/TOOL_VERSION_COMPATIBILITY.md)). A Yeoman generator (`generator-pptb`) and a `sample-tools` repo are the starter templates ([org repos](https://github.com/PowerPlatformToolBox)).

### Catalog: how it is built and reviewed

- **Observed.** The author publishes to npm (`npm publish --access public`). They test the published package through the in-app Debug "Install from npm" (pnpm), then submit the npm name and up to 3 categories on `powerplatformtoolbox.com/submit-tool` while signed in. Automated checks follow: the package exists, metadata, license, known vulnerabilities, structure. Then a manual review: "Security (no malicious code)", quality, function, docs, "typically 48-72 hours" ([Publishing Your Tool](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/publishing/page.mdx)).
- **Observed.** Conversion runs in CI. The `Convert and Publish Tool` workflow does `npm pack <name>`, then `npm install --omit=dev --omit=optional --ignore-scripts`, then `npm run --if-present build`. It deletes `.map` and non-`.d.ts` `.ts` files and tars **only `package.json` and `dist/`**. It then computes a SHA-256 and size, uploads to Azure Blob `packages/<id>-<version>/`, regenerates `registry.json`, and writes the release through a restricted Supabase RPC. The tool id is the npm name with `@` stripped and `/` turned into `-` ([convert-tool.yml](https://github.com/PowerPlatformToolBox/tool-management/blob/9e20244f1dc8bf8770a4ca89adae68001f5e534e/.github/workflows/convert-tool.yml)).
- **Inference.** The artifact users run is built by PPTB's CI from the npm tarball, not signed by the author. Runtime dependencies must already be bundled in `dist/`, because `node_modules` never reaches the archive. This matches the docs line "Registry packages should be self-contained" ([Tool Installation](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-installation/page.mdx)).
- **Observed.** For updates, a cron job (`0 0 * * *`) compares each tool's current release with `npm view <pkg> version` and records a `tool_updates` row ([check-updates.yml](https://github.com/PowerPlatformToolBox/tool-management/blob/9e20244f1dc8bf8770a4ca89adae68001f5e534e/.github/workflows/check-updates.yml)). The `update-tool` API then re-runs `validatePackageJson`. On errors it emails the admin and the developer and marks the update `validation_failed`. Otherwise it cancels any open Verified request, marks the update `validated`, and dispatches the convert workflow. **No human step appears in this path** ([app/api/update-tool/route.ts](https://github.com/PowerPlatformToolBox/pptb-web/blob/addbcac0259bc8a129ef56bc10e0cd8a3e097813/app/api/update-tool/route.ts)). The docs agree: "The ToolBox registry automatically syncs with npm."
- **Observed.** There are two trust tiers. Every listed tool starts **Unverified**. **Verified** is a separate human review requested from "My Tools", with a 1-2 week SLA and a single approve/reject email. The required checks are: README with screenshots, a documented reason for each CSP exception, no critical or high `npm audit` CVEs, no deprecated PPTB APIs, theme support, a bundled SVG icon, version ≥ 1.0.0, bug-response health (any bug >30 days without a maintainer reply blocks), an active contributor, and 2 of 3 usage metrics (MAU ≥ 10, downloads ≥ 50, one rating ≥ 3). Nightly governance **removes the badge immediately** for a new critical or high CVE or a **new CSP exception**. Bug-health breaches get a 2-week grace period, and so does an unaddressed breaking API change after release. Any update cancels a queued request. Reinstatement always means a full re-review ([Tool Maturity Model](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/maturity-model/page.mdx); [maturityGovernance.js](https://github.com/PowerPlatformToolBox/tool-management/blob/9e20244f1dc8bf8770a4ca89adae68001f5e534e/buildScripts/maturityGovernance.js)).
- **Observed.** Users can rate tools in the app without signing in, and can "Report a Concern" (spam, malicious, inappropriate, community values, other). A report carries the tool id and version, the maturity status, the app version and an anonymous install id ([Report a Concern](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-installation/report-a-concern/page.mdx)).
- **Observed.** The marketplace policy governs listings. It bans publisher branding in `displayName` (the npm scope carries the publisher), suite names, implied endorsement, borrowed names, keyword stuffing and near-duplicates. It requires credit and license compliance for ports of XTB tools, including AI-assisted ports. Destructive tools must preview first, confirm with the named environment and scope, and offer a way back. Data may go only to declared endpoints ([Marketplace Policy](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/policies/marketplace/page.mdx)).
- **Observed.** Private marketplaces: one or more HTTPS `registry.json` sources with a `tools` array (`id`, `name`, `version`, `downloadUrl` to a `.tar.gz`, `status`, `authors`). v1 authenticates only through URLs that carry read-only SAS tokens. A private entry **with the same `id` overrides the built-in one**. The built-in source can be disabled once a private source is enabled ([Private Marketplace](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-installation/private-marketplace/page.mdx)).

### Install, update and compatibility

- **Observed.** The client reads the registry from Supabase, falling back to Blob `registry.json` and then to a bundled local copy, and merges any private sources ([toolRegistryManager.ts L368-L763](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/src/main/managers/toolRegistryManager.ts#L368-L763)). On install it downloads to a staging directory, follows one redirect (http or https), extracts with the system `tar`, reads `package.json` and `pptb.config.json`, and moves the result into place ([L814-L1096](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/src/main/managers/toolRegistryManager.ts#L814-L1096)).
- **Observed.** The registry entry includes `checksum`. In this file, though, the only uses of `checksum` are passing it through, and there is no `createHash`/`sha256` call. The download and extract path does not verify it.
- **Observed.** An update is offered when the registry version is greater than the installed one ([L1342-L1360](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/src/main/managers/toolRegistryManager.ts#L1342-L1360)). The docs say updates are atomic and that a failed update keeps the old version ([Tool Installation](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-installation/page.mdx)).
- **Observed.** Compatibility: a tool is supported when it has no `minAPI`, or when `minAPI ≥ MIN_SUPPORTED_API_VERSION` (currently `"1.0.17"`) and `minAPI ≤ app version` ([versionManager.ts](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/src/main/managers/versionManager.ts); [constants.ts L47](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/src/main/constants.ts#L47)). Each API reference entry has a "Requires vX.Y.Z" badge, and authors are told to set `minAPI` to the highest one they use ([Manifest](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/manifest/page.mdx)). Removal policy: mark `@deprecated`, wait, then raise the floor ([TOOL_VERSION_COMPATIBILITY.md](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/docs/TOOL_VERSION_COMPATIBILITY.md)).
- **Inference.** This has the same weakness as XTB. `minAPI` means both "lowest host I need" and "API generation I target". A tool that sets `minAPI` low to reach more users looks as if it uses removed APIs, and a tool with no `minAPI` is always treated as compatible.

### Hosting and Host API

- **Observed.** Each tool instance is an Electron `BrowserView` with `contextIsolation: true`, `nodeIntegration: false`, **`sandbox: false`** ("so CommonJS require works" in the preload) and **`webSecurity: false`** ("to bypass CORS for external API calls") ([toolWindowManager.ts L458-L471](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/src/main/managers/toolWindowManager.ts#L458-L471)). Content is served from a privileged `pptb-webview://` scheme, and the host **injects a CSP `<meta>` tag** built from the tool's consented `cspExceptions` into the tool's HTML ([browserviewProtocolManager.ts L38-L139](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/src/main/managers/browserviewProtocolManager.ts#L38-L139)).
- **Conflict.** The docs architecture page still describes iframes and `postMessage` and lists Electron 28 ([Architecture](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/toolbox-development/desktop/architecture/page.mdx)). The source is the authority on current behaviour.
- **Inference.** Two things limit this design. A meta-tag CSP only applies to markup after the tag, and the host inserts it at `</head>`. And with `webSecurity: false`, CORS is no longer a backstop. Issue #760 confirms from outside that undeclared hosts are blocked while declared hosts are readable even without CORS headers ([desktop-app#760](https://github.com/PowerPlatformToolBox/desktop-app/issues/760)).
- **Connections. Observed.**
  - `toolboxAPI.connections.getActiveConnection/getSecondaryConnection/getConnections/getConnection(target)` return `{id, name, url, environment: Dev|Test|UAT|Production, colors, ...}`, with **no token**. `ToolContext` says tokens are excluded on purpose ([toolboxAPI.d.ts](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/packages/types/toolboxAPI.d.ts)).
  - Every `dataverseAPI` method takes an optional `connectionTarget`: `'primary'`, `'secondary'`, or a slot index capped by the manifest `connections` max. The API covers CRUD, `createMultiple`/`updateMultiple`, `executeBatch`/`executeTransaction`, FetchXML/OData queries, metadata reads, CSDL, and schema writes for tables, columns, relationships and option sets ([Dataverse API](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/api-reference/dataverse-api/page.mdx)).
  - `powerplatformAPI` needs `enabledForPowerPlatformAPI`.
- **Multiple connections. Observed.** These are declared in the manifest (`connections: 2` or `{min:1,max:3}`). The host's connection picker collects `min` before launch, and the rest up to `max` are optional ([Manifest](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/manifest/page.mdx)). They grew from one to two to N because authors porting XTB tools such as Solution Transfer needed "multiple downstream connections" ([desktop-app#554](https://github.com/PowerPlatformToolBox/desktop-app/issues/554), [#110](https://github.com/PowerPlatformToolBox/desktop-app/issues/110)).
- **Settings. Observed.** `toolboxAPI.settings.get/set/getAll/setAll` stores key/value pairs per tool ([Settings API](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/api-reference/settings-api/page.mdx)). Uninstall removes "any stored preferences" ([Tool Installation](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-installation/page.mdx)).
- **Files. Observed.** `fileSystem.readText/readBinary/exists/stat/readDirectory/writeText/createDirectory/saveFile/selectPath` work only on paths the user chose through `selectPath`/`saveFile`, or their descendants. Grants are per tool instance and revoked on close ([toolFileSystemAccessManager.ts](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/src/main/managers/toolFileSystemAccessManager.ts)). Callers are identified by their `WebContents`, not by an argument they pass ([filesystemAuthorization.ts](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/src/main/utils/filesystemAuthorization.ts)).
- **Notifications and other host services. Observed.** `utils.showNotification`, `copyToClipboard`, `getCurrentTheme`, `openInConnectionBrowser`; an `events` API (`tool:*`, `connection:*`, `settings:updated`, `terminal:*`, with history); `preventClose`/`releasePreventClose`; a **terminal API that creates shells and executes commands**; and inter-tool invocation (`launchTool`, `findToolsByCapability`, `returnData`) ([toolboxAPI.d.ts](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/packages/types/toolboxAPI.d.ts)).
- **.NET workers. Observed.** These are framework-dependent .NET tool packages fetched from the nuget.org flat container by exact id and version. They run as child processes speaking JSON-RPC over stdio and need **native-code consent**, whose fingerprint includes the source path and the package SHA-512. Workers never receive tokens and must call Dataverse back through the UI ([DOTNET_WORKERS.md](https://github.com/PowerPlatformToolBox/desktop-app/blob/152f482d92369a8ec49dc8479f1c4f22447452c6/docs/DOTNET_WORKERS.md)). **Inference.** Unlike our tool workers, these are not sandboxed. Consent is the only control.
- **Permission consent. Observed.** On first launch, or when an update adds permissions, a dialog lists the CSP exceptions. Only new items need a decision, and previously approved ones are shown read-only. If the user declines, the tool does not load ([Tool Installation](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-installation/page.mdx); [desktop-app#157](https://github.com/PowerPlatformToolBox/desktop-app/issues/157)).

### Reported pain points

- **Tools needing other APIs have no credential path. Observed.** A tool that needs Azure Monitor can reach the declared host but cannot get a token for it. It would have to run its own device-code sign-in and keep tokens in its own JavaScript. The proposal is host-proxied calls per audience with a fixed host allow-list ([desktop-app#760](https://github.com/PowerPlatformToolBox/desktop-app/issues/760), 2026-11-02).
- **Corporate TLS inspection breaks downloads. Observed.** Behind Zscaler, tool downloads fail because Node's CA store does not trust the inspection root ([#555](https://github.com/PowerPlatformToolBox/desktop-app/issues/555)).
- **The developer install path is fragile. Observed.**
  - npm installs from the Debug menu load but then fail to open ([#638](https://github.com/PowerPlatformToolBox/desktop-app/issues/638)).
  - `spawn EINVAL` on Windows 1.2.7 when installing by package ([#741](https://github.com/PowerPlatformToolBox/desktop-app/issues/741)).
  - The docs require pnpm on the user's machine for npm or local installs ([Tool Installation](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-installation/page.mdx)).
- **Feature parity pressure from XTB. Observed.** There is an open checklist for XTB settings parity ([#279](https://github.com/PowerPlatformToolBox/desktop-app/issues/279)). CSP UX needed several fixes: wording, scrolling, an "optional" flag, author-written reasons ([#391](https://github.com/PowerPlatformToolBox/desktop-app/issues/391), [#212](https://github.com/PowerPlatformToolBox/desktop-app/issues/212), [#393](https://github.com/PowerPlatformToolBox/desktop-app/issues/393), [#392](https://github.com/PowerPlatformToolBox/desktop-app/issues/392)).
- **Manifest churn. Observed.** `iconURL` → `icon`, and `multiConnection`/`connectionRequirement` → `connections`. Both are kept as deprecated paths with validator warnings ([Manifest](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/manifest/page.mdx)).

## Conflicts between sources

- **PPTB `icon` and `readmeUrl`: required or optional?** The manifest and publishing pages list `icon` as required and `readmeUrl` as optional. The validator page says the reverse: `icon` is a warning-level optional field and `configurations.readmeUrl` is a required error-level field ([Validation](https://github.com/PowerPlatformToolBox/pptb-docs-web/blob/22cce93c9250ccc0ebcffa5844343356355cc5d8/src/app/tool-development/validation/page.mdx)). The Verified checklist requires an icon. I did not read `packages/validation/src/validate.ts`, which would settle what intake actually enforces.
- **PPTB isolation.** The docs say "separate iframe". The source uses `BrowserView` with `sandbox: false` (see above). I take the source as authoritative.
- **XTB review of updates.** The official page requires admin validation for listing. A third-party package page claims there is "no separate approval step" ([DataMigrationToolbyXTB on NuGet](https://www.nuget.org/packages/DataMigrationToolbyXTB)). That page is one author's account, so I do not rely on it. My best guess is that it describes new versions of an already-validated tool. That is an inference, not something either source confirms.

## What the evidence cannot establish

- Whether XTB's portal re-reviews new versions of a validated tool, how often it syncs from NuGet, and how `mctools_files` is computed. The server side is not public.
- Whether PPTB verifies `checksum` anywhere at all. I searched `toolRegistryManager.ts` and `toolsManager.ts`, and both only pass the value along. Other main-process files were not searched, so the finding is "not verified in the install path I read", not "never verified".
- Real-world rates: how many XTB or PPTB tools break per host release, review rejection rates, and how often the Verified badge is revoked.
- PPTB terminal API consent: whether `terminal.create`/`execute` asks the user first. I did not find a consent manager for it in the files I read.

## Lessons for Power Tools (recommendations)

These are ranked by how directly they affect our Host API, package format and catalog decisions.

1. **Package format: ship a built, self-contained bundle, and let the catalog verify an exact digest and a publisher signature on every install and update.** Neither toolbox checks integrity at install in the code I read. XTB has no check. PPTB records a SHA-256 but does not compare it in the download path, and it rebuilds author packages in its own CI. Our package should hold the UI bundle, the tool worker scripts and the manifest. Dependencies should be bundled, not resolved at install (PPTB's archive already drops `node_modules`). The catalog entry should pin a digest, and the app should refuse a mismatch. Publisher verification should be a signature over that digest, not over a CI rebuild. PPTB's .NET-worker path (an exact version, a SHA-512 in the consent fingerprint, a fresh approval when bytes change) is the model to copy for the whole package.
2. **Manifest: keep "lowest host I need" separate from "SDK/API generation I target", and declare capabilities, not just URLs.** Both hosts fold these into one number, `minAPI` or the `XrmToolBox` dependency, against a global floor. Retiring old API then strands every older tool at once, and a tool with no value counts as compatible. Proposed fields:
   - `engines.powerTools` (a host range) for "lowest host I need".
   - `sdkVersion`, written by the typed npm SDK at build time, for the API generation.
   - An explicit list of Host API capabilities the tool uses: connections count/range, `files`, `network` origins with reasons, Power Platform/other audiences, workers.

   The host can then grade compatibility per capability, and the consent dialog can be generated from the manifest. PPTB's `connections: {min,max}` and `cspExceptions` with `exceptionReason` and `optional` are good shapes to borrow.
3. **Host API: proxy every credentialed call and never hand out tokens; give each tool a stable identity derived by the host.** PPTB shows the right direction. Tokens are kept out of `ToolContext`. File grants are bound to the caller's `WebContents` and to user-picked paths. Dataverse calls take a `connectionTarget` slot. Its biggest open request (#760) is the same pattern for other audiences, so the Host API should define an extension point for "host-acquired token for audience X, fixed host allow-list, response only" from v1 instead of adding audiences one at a time. Avoid the weaknesses we found: `sandbox: false`, `webSecurity: false`, a CSP injected as a meta tag, and an open shell API. Apply CSP and network policy from the host (response headers or a session request filter) where the tool cannot get around them.
4. **Catalog: tie review to the version, not only to the tool, and surface what changed.** PPTB reviews a tool once by hand, then automatically republishes every new npm version after metadata validation alone. Its only per-update guards are re-consent for new permissions and losing the badge. XTB's update review is undocumented. For us, a new version that adds capabilities (a new origin, a new audience, workers, more connections) should go back to review, or at least hold the update until the user consents. A version with no capability change can flow automatically if it is signed by the verified publisher. Two-tier trust (listed vs verified) with nightly governance (revoke on a new high CVE or a new network origin) is worth copying, and so is the "Report a concern" entry point in the app.
5. **Isolation and lifecycle: no shared dependency space, no restart to update, private catalogs that cannot shadow public ids.**
   - XTB's worst user pain is one Plugins folder and one AppDomain, where one tool's DLL breaks another. Each community tool should have its own directory, origin and storage, and uninstall should remove all of it.
   - Updates should be a staged install plus an atomic swap, applied when the tool's tabs close, with no app restart.
   - For enterprise private catalogs (XTB uses registry keys, PPTB uses SAS-token sources), do not let a private entry silently replace a public tool with the same id, as PPTB does. Namespace ids by publisher, and keep an admin allow-list policy like XTB's `AllowedPlugins`.

Smaller points for the starter template and dev mode:

- Ship the review rules as a CLI inside the SDK, as PPTB's `pptb-validate` does, so authors see intake failures before they publish.
- Make the dev-mode "load from folder" path need no package manager on the user's machine. PPTB's pnpm requirement produces repeated install bugs.
- Read the OS certificate store for catalog downloads (PPTB#555).
- Adopt policy text early: naming without publisher prefixes, credit for ports, and preview-and-confirm rules for destructive operations.
